# 扩展逻辑与外部程序控制

本文说明如何让 Auto Theme Switcher 在亮色/暗色切换后执行其他逻辑，或把新的 macOS 程序纳入自动控制。

## 先了解当前边界

当前版本不是动态插件系统，也不会扫描用户脚本。新增能力需要修改 Swift 源码、补测试并重新打包 App。

环境光状态机只负责产生 `.light` 或 `.dark` 请求；真正的切换入口在：

```text
Sources/AutoThemeSwitcher/AppController.swift
  beginThemeSwitch(to:origin:)
    -> ThemeTransactionCoordinator.switchTheme(to:)
```

现有 VS Code 和 Ghostty 通过以下协议接入：

```text
Sources/AutoThemeSwitcherCore/ThemeTransaction.swift
  ThemeAdapter
  RestorableThemeAdapter
  ThemeTransactionCoordinator
```

因此扩展通常有两条路径：

| 需求 | 推荐方式 |
| --- | --- |
| 切换成功后发通知、调用脚本、请求本地 API、触发快捷指令 | 增加“切换后动作” |
| 修改另一个程序的配置文件，并要求校验、回滚和崩溃恢复 | 实现 `RestorableThemeAdapter` |
| 仅让运行中的程序重载刚写好的配置 | 在适配器 `commit` 后调用该程序的 reload 能力 |
| 控制不可回滚的外部设备或服务 | 作为切换后动作处理，不要伪装成原子文件事务 |

## 方案一：增加切换后动作

这适合“主题事务已经成功，再执行一项附加逻辑”。例如：

- 运行固定的本地可执行文件；
- 执行 macOS Shortcut；
- 通过 Apple Events 控制另一个 App；
- 调用 `localhost` 上的 HTTP 服务；
- 发送系统通知或写入自己的状态文件。

### 1. 定义动作接口

可在 `Sources/AutoThemeSwitcherCore/` 新建 `ModeAction.swift`：

```swift
import Foundation

public protocol ModeAction: Sendable {
    var identifier: String { get }
    func run(for mode: ThemeMode) async throws
}
```

如果动作只是调用固定命令，可以按下面的方向实现：

```swift
import Foundation

public enum CommandModeActionError: LocalizedError, Sendable {
    case failed(status: Int32, message: String)

    public var errorDescription: String? {
        switch self {
        case let .failed(status, message):
            "命令退出状态为 \(status)：\(message)"
        }
    }
}

public struct CommandModeAction: ModeAction {
    public let identifier: String
    public let executableURL: URL
    public let lightArguments: [String]
    public let darkArguments: [String]

    public init(
        identifier: String,
        executableURL: URL,
        lightArguments: [String],
        darkArguments: [String]
    ) {
        self.identifier = identifier
        self.executableURL = executableURL
        self.lightArguments = lightArguments
        self.darkArguments = darkArguments
    }

    public func run(for mode: ThemeMode) async throws {
        let arguments = mode == .light ? lightArguments : darkArguments
        try await Task.detached(priority: .utility) {
            let process = Process()
            process.executableURL = executableURL
            process.arguments = arguments

            let errorPipe = Pipe()
            process.standardError = errorPipe
            try process.run()
            process.waitUntilExit()

            guard process.terminationStatus == 0 else {
                let data = errorPipe.fileHandleForReading.readDataToEndOfFile()
                let message = String(data: data, encoding: .utf8) ?? "无错误输出"
                throw CommandModeActionError.failed(
                    status: process.terminationStatus,
                    message: message
                )
            }
        }.value
    }
}
```

正式实现还应增加超时、输出长度上限和取消处理。不要使用 `/bin/sh -c` 拼接用户输入；应固定 `executableURL`，并把参数逐项放入 `arguments`，避免 shell 注入和 PATH 不一致。

### 2. 在成功切换后调用

在 `AppController` 中持有动作列表：

```swift
private let postSwitchActions: [any ModeAction]
```

然后在 `beginThemeSwitch(to:origin:)` 中，仅当下面这一步成功后再执行动作：

```swift
let result = try await transactionCoordinator.switchTheme(to: mode)
```

建议调用顺序为：

1. 完成 VS Code、Ghostty 和其他配置型适配器的事务；
2. 确认 `displayedMode` 并保存当前模式；
3. 依次执行切换后动作；
4. 动作失败时显示警告，但不要回滚已经成功的主题事务。

可增加一个集中方法，避免每个调用点各写一套错误处理：

```swift
private func runPostSwitchActions(for mode: ThemeMode) async -> [String] {
    var warnings: [String] = []
    for action in postSwitchActions {
        do {
            try await action.run(for: mode)
        } catch {
            warnings.append("\(action.identifier)：\(error.localizedDescription)")
        }
    }
    return warnings
}
```

需要明确动作在哪些场景运行。当前项目有三个相关入口：

| 场景 | 当前方法 | 通常是否运行附加动作 |
| --- | --- | --- |
| 自动或手动切换 | `beginThemeSwitch(to:origin:)` | 是 |
| “安装或修复集成”同步当前模式 | `installIntegration()` | 按需求决定 |
| “恢复并停用”恢复暗色 | `restoreAndDisable()` | 建议单独定义恢复行为，不要默认当作普通暗色切换 |

若动作只应响应自动切换，可检查 `SwitchOrigin.automatic`；若手动按钮也应触发，则两种 origin 都执行。

### 3. 常见控制方式

#### 固定 CLI 或 Shortcut

控制 Shortcuts 的命令形式为：

```text
/usr/bin/shortcuts run <快捷指令名称> --input-path <固定输入文件>
```

在 Swift 中仍应使用 `Process.executableURL = URL(fileURLWithPath: "/usr/bin/shortcuts")` 和独立参数，不依赖交互式 shell 环境。

#### AppleScript / Apple Events

项目中的 `AppleScriptGhosttyReloader` 已提供可参考的实现：先判断目标程序是否正在运行，再执行动作，不主动启动目标程序。

控制新的 App 时还需要：

1. 确认目标 App 的 scripting dictionary 确实提供所需命令；
2. 更新 `Config/Info.plist` 中 `NSAppleEventsUsageDescription`，使说明覆盖新增用途；
3. 保留 `Config/AutoThemeSwitcher.entitlements` 中的 `com.apple.security.automation.apple-events`；
4. 重新签名并运行，接受 macOS 首次 Automation 授权；
5. 明确处理“目标未运行”“用户拒绝权限”“目标不支持该命令”三种情况。

不要用 UI 坐标点击代替正式接口。若目标程序没有 AppleScript、CLI、URL Scheme 或本地 API，才考虑 Accessibility；这会引入更高权限、更多系统设置步骤和更脆弱的 UI 依赖。

#### 本地 HTTP / Socket

只连接明确的本机地址，设置连接与总超时，并校验响应。若接口能执行敏感操作，应使用随机令牌或 Unix Domain Socket 权限控制；不要把令牌写进诊断摘要或错误日志。

## 方案二：把新程序加入主题事务

如果新程序通过配置文件切换主题，建议实现 `RestorableThemeAdapter`。这样它会与 VS Code、Ghostty 一起执行：

```text
inspect -> prepare -> 写入事务日志 -> commit -> verify
                                  失败 -> reverse rollback
```

App 意外退出后，`transaction-journal.json` 还可驱动安全恢复。

### 1. 各方法的职责

| 方法 | 允许做什么 | 不应做什么 |
| --- | --- | --- |
| `inspect()` | 只读配置、判断当前模式和冲突 | 改文件、启动程序 |
| `prepare(...)` | 基于快照生成候选内容和哈希 | 写入最终配置 |
| `commit(...)` | 用 CAS 提交已准备的文件变更 | 重新读取后盲目覆盖 |
| `verify(...)` | 校验候选哈希和实际语义 | 把失败静默当成功 |
| `rollback(...)` | 仅在文件仍等于候选哈希时恢复 | 覆盖用户在提交后的新修改 |
| `prepareRestoration(...)` | 生成“恢复并停用”的逆迁移 | 无条件删除用户配置 |

状态含义：

- `.ready`：集成完整，可以安全切换；
- `.needsInstallation`：只有用户点击“安装或修复集成”时才允许创建托管内容；
- `.unavailable`：目标程序或配置不存在；
- `.conflict`：发现未知、重复或被外部修改的托管内容，必须停止写入。

### 2. 最小适配器骨架

下面是文件型适配器的结构示意，解析和生成配置的部分应替换成目标程序的真实格式：

```swift
import Foundation

public struct OtherAppThemeAdapter: RestorableThemeAdapter {
    public let identifier = "other-app"
    public let transactionOrder = 10

    private let configURL: URL
    private let fileSystem: any ThemeFileSystem
    private let executor: ThemeMutationExecutor

    public init(
        configURL: URL,
        fileSystem: any ThemeFileSystem = LocalThemeFileSystem()
    ) {
        self.configURL = configURL.standardizedFileURL
        self.fileSystem = fileSystem
        self.executor = ThemeMutationExecutor(fileSystem: fileSystem)
    }

    public func inspect() throws -> ThemeInspection {
        let snapshot = try fileSystem.snapshot(at: configURL)
        guard let data = snapshot.data else {
            return ThemeInspection(
                adapterIdentifier: identifier,
                detectedMode: nil,
                status: .unavailable,
                files: [snapshot],
                message: "找不到目标程序配置"
            )
        }

        let mode = try parseMode(from: data)
        return ThemeInspection(
            adapterIdentifier: identifier,
            detectedMode: mode,
            status: .ready,
            files: [snapshot]
        )
    }

    public func prepare(
        targetMode: ThemeMode,
        from inspection: ThemeInspection
    ) throws -> PreparedThemeChange {
        guard inspection.adapterIdentifier == identifier,
              inspection.status == .ready,
              let snapshot = inspection.snapshot(for: configURL),
              let original = snapshot.data
        else {
            throw OtherAppError.invalidInspection
        }

        let candidate = try replacingMode(in: original, with: targetMode)
        let mutations = candidate == original ? [] : [
            PreparedThemeMutation(
                snapshot: snapshot,
                candidateData: candidate,
                label: "Other App 主题配置"
            )
        ]
        return PreparedThemeChange(
            adapterIdentifier: identifier,
            targetMode: targetMode,
            mutations: mutations
        )
    }

    public func commit(_ change: PreparedThemeChange) throws -> ThemeCommitReceipt {
        guard change.adapterIdentifier == identifier else {
            throw OtherAppError.wrongChange
        }
        return try executor.commit(change)
    }

    public func verify(_ receipt: ThemeCommitReceipt) throws {
        try executor.verify(receipt)
        guard try inspect().detectedMode == receipt.change.targetMode else {
            throw OtherAppError.verificationFailed
        }
    }

    public func rollback(_ receipt: ThemeCommitReceipt) throws {
        try executor.rollback(receipt)
    }

    public func prepareRestoration(
        from inspection: ThemeInspection
    ) throws -> PreparedThemeChange {
        // 应只撤销本适配器拥有的字段。若无法证明所有权，应返回冲突而不是删除。
        try makeRestorationChange(from: inspection)
    }
}
```

这段代码是接入骨架，不包含目标配置格式、ownership 标记和错误枚举。正式实现应参考：

- `VSCodeThemeAdapter.swift`：JSONC 字段级修改、逐字节备份和 ownership manifest；
- `GhosttyThemeAdapter.swift`：托管标记、独立 overlay 文件、外部语法验证和 reload；
- `ThemeTransactionTests.swift`：CAS 冲突、逆序回滚和崩溃恢复测试。

### 3. 注册适配器

在 `AppController` 的 convenience initializer 中实例化并加入数组：

```swift
let otherApp = OtherAppThemeAdapter(configURL: paths.otherAppConfiguration)

self.init(
    // ...
    adapters: [ghostty, otherApp, vscode],
    initialMode: initialMode
)
```

当前 `AppController.adapters` 的类型是 `[any RestorableThemeAdapter]`，所以注册到这里的正式集成必须支持“恢复并停用”。`transactionOrder` 越小越早提交；失败时按相反顺序回滚。每个 `identifier` 必须唯一。

若路径属于固定的当前用户配置，应在 `AppPaths` 增加字段，而不是把 Home 目录拼接逻辑散落到适配器和 UI 中。

### 4. 把新程序接入状态和 UI

只把适配器放进数组还不够。当前 UI 和对齐判断仍明确列出 `vscode`、`ghostty`。要成为完整的一等集成，还需同步修改：

- `AppController.inspectIntegrations(syncDetectedMode:)` 的模式同步集合；
- `integrationInstalled`、`themesAreAligned`、`integrationNeedsInstallation`；
- `computeIntegrationError()` 的检查顺序；
- 新程序的 `@Published` 状态、诊断摘要和打开配置方法；
- `MenuBarContentView` 的状态行及配置按钮；
- 首次安装、恢复、冲突和目标程序缺失的测试。

建议把硬编码 identifier 数组提取为统一的 `requiredAdapterIdentifiers`，避免以后加了适配器却漏改某个判断。

## 外部副作用为什么不能直接塞进文件事务

事务日志完整记录的是 `PreparedThemeMutation`，也就是可哈希、可比较、可恢复的文件变更。Apple Event、HTTP 请求、设备控制或任意命令已经发生后，通常无法从文件哈希判断其外部状态。

因此不要仅仅实现一个“没有 mutations、但在 `commit` 里发命令”的适配器，并宣称它拥有崩溃恢复能力。进程可能在命令已执行、receipt 尚未写入 journal 时退出，恢复逻辑无法判断是否需要反向操作。

只有同时满足以下条件时，才适合把外部控制升级为事务参与者：

- 目标接口可读取当前状态；
- 设置操作幂等；
- 可以记录旧状态和目标状态；
- 回滚操作可靠且有验证；
- App 重启后能根据持久化记录重新对账。

否则应把它定义为“切换后动作”，允许独立失败、重试并在菜单中显示警告。

## 安全与可靠性检查清单

新增逻辑交付前至少确认：

- `inspect` 和 `prepare` 不写最终配置；
- 每次写入都基于刚检查过的哈希，外部修改时立即停止；
- 只管理带明确 ownership 标记或 manifest 的字段；
- 不把用户输入拼进 shell 命令；
- 外部命令有超时，不会卡住菜单栏主线程；
- Apple Events 的权限说明与实际用途一致；
- 目标程序未安装、未运行、权限被拒绝时都有清晰提示；
- 自动切换与手动切换是否触发附加动作已经明确；
- “恢复并停用”不会删除用户自定义内容；
- 测试不触碰真实用户配置，也不实际控制用户正在运行的程序。

## 建议的测试范围

文件适配器应覆盖：

1. 亮色和暗色候选内容；
2. 无配置、未安装和冲突状态；
3. prepare 后文件被外部修改时拒绝 commit；
4. verify 失败触发跨适配器逆序回滚；
5. rollback 不覆盖提交后的第三方修改；
6. 崩溃 journal 能恢复候选文件；
7. restoration 只撤销自己拥有的内容。

切换后动作应使用 fake 或 spy 实现测试，不应在 `swift test` 中执行真实 Apple Event、快捷指令、HTTP 控制或外部设备命令。至少覆盖亮/暗参数映射、超时、非零退出码、权限拒绝以及一个动作失败后错误如何展示。

## 推荐实施顺序

1. 先确认目标程序公开的稳定控制面：配置文件、CLI、AppleScript、URL Scheme 或本地 API；
2. 明确触发时机以及失败是否应影响主题切换；
3. 配置型控制实现 `RestorableThemeAdapter`，其他副作用实现切换后动作；
4. 用依赖注入隔离文件系统、进程执行器或 API 客户端；
5. 补冲突、回滚、权限和超时测试；
6. 更新菜单状态、诊断摘要、权限说明和 README；
7. 运行 `swift test`，再打包 App 做一次真实权限验证。
